이미 연결된 서비스, 빠져 있던 개인정보 기준

03

DECISION · 무엇을 골랐나

기존 사업가치를 유지해야 한다는 제약 안에서, 법률 · K제약 · 개발 · 영업의 요구를 하나의 실행 가능한 서비스 규칙으로 정리. 네 결정 중 기준이 된 것은 D1 흐름 유지와 D2 동의 상태 연결.

D1

기능은 유지하고, 정보가 오가는 조건을 새로 정함

대안

문제 되는 연동 기능 삭제 → 정보 전달 자체를 없앰

선택

지금 쓰는 흐름은 그대로 두고, 어떤 조건에서 정보를 넘길지를 규칙으로 정함.

이유

지우면 파트너몰에서 케어팜으로 가입하는 길, K제약 VIP 혜택, 케어팜에서 확인하고 파트너몰에서 주문하는 길이 함께 사라짐. 약국이 지금 쓰고 있는 경로.

포기한 것

선택 흐름 유지 → 포기 기능 삭제로 얻는 단순함 → 대가 가입 경로 · 진행 상태 · 동의 상태를 계속 관리하고, 개발 · 기록 · 내부 운영 절차까지 설계 범위에 포함. 그 대신 쓰던 흐름 유지 · 개인정보 처리 기준 명확화.

D2

동의 상태가 정보 전달 여부를 결정하게 함

대안

가입 · 주문 화면에 체크박스를 넣고 동의했는지만 저장

선택

동의 상태를 확인해야만 정보가 넘어가도록 연결.

이유

체크박스는 '동의를 받았다'는 사실만 남김. 정보가 실제로 넘어가는 시점은 화면 이후의 시스템 처리 — 그 시점에 확인해야 실제로 막을 수 있음.

포기한 것

선택 동의 상태와 전달 연결 → 포기 체크박스 저장의 단순함 → 대가 정보가 넘어가는 모든 지점에서 동의 상태 확인, 상태 · 처리 · 기록 설계가 함께 따라옴. 그 대신 조건이 맞을 때만 정보 전달.

D3

이미 케어팜 회원인 약국이 약정을 맺으면, 기존 회원에 자격만 추가

대안

가입할 때의 경로로 회원 종류를 고정

선택

가입 상태와 제휴 자격을 따로 관리. 기존 회원이 나중에 약정을 맺으면 VIP 자격만 붙임.

이유

이미 케어팜을 쓰던 약국이 나중에 협력도매 약정을 맺는 경우가 있음. 가입 시점 경로로 고정하면 이 약국은 자격을 받을 방법이 없음.

포기한 것

선택 가입과 자격 분리 → 포기 회원 종류 고정의 단순함 → 대가 가입 상태와 자격, 두 가지를 함께 관리. 그 대신 기존 회원의 약정 추가 가능.

D4

사람이 처리하는 내부 절차까지 설계 범위에 포함

대안

약국이 보는 가입 화면까지만 기획

선택

신청 → 확인 → 영업 상담 → 가입으로 이어지는 절차를 함께 설계.

이유

자격 없이 신청한 경로는 화면 밖의 확인과 상담을 거쳐야 가입이 성립.

포기한 것

선택 운영 절차 포함 → 포기 화면 기획만의 좁은 범위 → 대가 기획 범위와 협의할 곳 증가, 영업 · 운영과의 합의가 일정에 들어옴. 그 대신 규칙이 현장에서 그대로 작동.

누구와 무엇을 정했나

함께 정한 곳정한 것
개인정보 · 법률무엇을 모으고 넘길 수 있는지, 어떻게 알릴지
K제약 · 파트너몰넘길 정보와 가입 경로
개발시스템 처리 조건 · 상태 · 기록
영업 · 운영신청 → 상담 → 가입 절차

네 곳의 결정이 서로 물려 있음. 법무가 정한 동의 기준이 넘길 정보 범위를 정하고, 그 범위가 시스템 처리 조건과 기록 항목을 정하고, 그 결과가 영업 상담에서 확인할 수 있는 범위를 정함. 그래서 각각의 요구를 하나의 서비스 규칙으로 통합.

04

HOW · 어떻게 만들었나

어떤 경로로 들어왔나 → 동의를 받았나 → 무엇을 보내나 → 지금 어디까지 왔나 → 기록에 남았나. 앞 규칙이 정해져야 뒤 규칙이 정해지도록 순서 고정. 규칙을 정한 순서가 곧 시스템이 확인하는 순서.

법적 요구를 시스템이 판단할 수 있는 조건으로 옮김 — 동의했는가는 진입 조건으로, 전달 항목은 보낼 항목 정의로, 진행 상태는 다음 단계를 여는 조건으로, 동의 시점은 기록으로.

서비스 규칙 — 가입 경로 → 동의 → 전달 항목 → 진행 상태 → 동의 기록

규칙내용
가입 경로협력도매 약정 → K제약 VIP, 일반 케어팜 메뉴 → 일반 K제약. 경로마다 다른 값을 함께 전달하고, 그 값을 근거로 관리자 화면에서 약국 구분
회원 구분신규 가입과 제휴 자격을 따로 관리. 기존 케어팜 회원이 이후 약정을 맺으면 신규 회원 생성 없이 VIP 자격만 추가 (D3)
전달 항목파트너몰 → 케어팜 가입 시 약국명 / 대표자명 · 약사면허번호 · 사업자등록번호 · 요양기관번호 · 주소 · 생년월일 · 전화번호 / 휴대폰번호 · 이메일 주소
동의파트너몰 → 케어팜 가입 신청 전 제3자 제공 동의 — 넘기는 항목 · 목적 · 보관 기간 · 동의 거부 시 안내. 케어팜 → 파트너몰 주문은 프로그램을 켤 때 연동 동의 팝업
진행 상태동의 전 → 동의 단계에 머무름. 동의 + 가입 신청 완료 → 약정 신청서 제출 가능. 기존 회원 + 약정 체결 → VIP 자격 부여. 자격 없이 신청 → 확인 · 영업 상담 절차로 연결
동의 기록동의 여부와 함께 동의한 시각 · 접속 IP · 동의한 항목 기록. "언제 무엇에 동의했는지"를 되짚을 수 있는 단위

전달 항목은 누구의 / 어떤 정보를 / 어디로 / 언제 보내는지를 경로 · 동의 · 회원 상태 · 지금 하려는 행동과 함께 보고 판단. 항목이 정해져야 동의 화면에 적을 안내 문구가 정해지고, 안내가 정해져야 동의가 성립.

시스템끼리 주고받는 상세 규격(API Spec)은 개발과 함께 확정 예정. 임시로 정하면 나중에 바꿀 때 경로 · 동의 · 전달 규칙 전체가 흔들린다.

NEXT · 한계와 다음 반복

이 프로젝트의 차별점은 기존 사업가치를 유지해야 한다는 제약 안에서, 법률 · K제약 · 개발 · 영업의 요구를 하나의 실행 가능한 서비스 규칙으로 정리한 과정. 규칙은 확정, 남은 것은 시스템끼리 주고받는 상세 규격(API Spec).

What changed my mind?

처음에는 동의 체크박스가 없다는 것이 문제로 보였음. 전수 확인을 거치고 나서 문제를 회원 구분 · 정보 전달 · 동의 · 진행 상태 · 기록이 서로 이어져 있지 않은 구조로 다시 정의 — 그래서 화면과 함께 규칙 · 상태 · 시스템 처리 · 기록까지 정함.

What I Learned

01

서비스 간 연동은 API 연결 + 기준 정의로 완성

누구인지 · 무엇을 보내는지 · 동의를 받았는지 · 지금 어디까지 왔는지 · 누가 책임지는지까지 정해야 연결이 완성.

02

법무 의견보다 Data Flow 전수 확인이 먼저

무엇이 오가는지 알아야 무엇에 동의를 받을지 정해짐. 네 갈래의 실제 전달 정보를 확인한 뒤에 규칙 순서가 정해짐.

03

규칙의 순서가 곧 설계

경로 → 동의 → 전달 항목 → 상태 → 기록. 앞 규칙이 뒤 규칙을 정하도록 고정하자 동의와 보낼 항목이 항상 함께 정해지는 구조가 됨.

04

B2B 연동은 화면 밖까지

자격 없는 신청은 확인 · 상담을 거쳐 가입이 완료됨. 관리자 목록 · 영업 상담까지 하나의 흐름으로 봐야 규칙이 실제로 작동.
