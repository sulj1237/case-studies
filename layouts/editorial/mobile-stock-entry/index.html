02

Problem — 재고가 되는 시점

문제는 모바일이 아니라 재고가 되는 시점이었다

기존에는 상품 등록과 재고 입력을 PC에서 처리해야 했습니다. 현장에서 상품을 확인하고 수량을 세더라도, 다시 PC로 돌아와 입력해야 했습니다.

기존 문제발생하는 상황
현장에서 입력할 수 없음상품을 확인한 뒤 PC로 이동
재입력 필요기억하거나 메모한 값을 다시 입력
여러 사용자가 함께 사용누가 무엇을 보냈는지 구분 필요
처리 결과를 알기 어려움반영 여부 확인 필요
입력값과 실제 재고가 달라질 수 있음판매·입고 사이에 값이 변할 수 있음

모바일을 추가하는 것보다 먼저, 입력된 값이 언제 실제 재고가 되는지 정의해야 했습니다.

04

Solution — 두 개의 역할

두 개의 역할로 나눴습니다

Mobile

현장에서 데이터를 만든다

바코드 스캔 · 상품 등록/수정 · 재고 수량 입력 · 제출 · 처리 결과 확인

PC

데이터를 검토하고 확정한다

제출 내용 확인 · 상품 변경 검토 · 재고 변경 검토 · 반영 / 반려

System

처리 과정을 남긴다

제출자 · 기기 · 제출 시점 · 처리 상태 · 반영/반려 결과를 남긴다

반영되지 않은 것도 기록으로 남아야 합니다. 반려도 하나의 결과로 기록합니다.

05

Why — 왜 바로 반영하지 않았나

D1

모바일 입력값을 실제 재고에 바로 반영하지 않는다

대안

입력 즉시 재고 반영

선택

입력 → 제출 → 검토 → 반영 / 반려

이유

현장은 서서 빠르게 입력하는 곳이라 잘못 누르는 일이 생긴다. 확인 단계가 있으면 틀린 값이 재고에 닿기 전에 걸린다.

포기한 것

빠른 즉시 반영은 포기했지만, 잘못 입력된 값이 실제 재고에 바로 영향을 주는 것을 막았습니다.

D2

모바일과 PC의 역할을 분리한다

대안

모바일에서도 기존 PC 기능을 모두 제공

선택

Mobile = Input / PC = Confirmation

이유

같은 기능이 양쪽에 있으면 어느 쪽 숫자가 맞는지 정할 수 없다. 역할을 나누면 최종 결정이 한 곳에서만 일어난다.

포기한 것

모바일만으로 업무를 끝내는 편의성은 포기했지만, 최종 재고를 확정하는 주체를 하나로 유지했습니다.

재고 숫자가 달라지는 경우

Mobile에서 본 재고 ≠ PC에서 반영할 당시 재고. 오류로 처리하지 않고 시간 차이에 따른 값의 차이로 정의합니다. 최종 재고는 반영 시점의 값을 기준으로 합니다.

06

Implementation — 어떻게 구현했나

  1. 1

    Mobile

    바코드를 찍고 상품·재고 수량을 입력해 보낸다

  2. 2

    PC

    제출 데이터를 확인하고 상품·재고 변경을 검토해 반영/반려한다

  3. 3

    Stock

    반영한 값만 실제 재고에 들어간다

바코드 → 상품/재고 입력 → 제출 → PC 검토 → 반영/반려 → 실제 재고 변경

상태 — 대기 → 처리 중 → 반영 / 반려

보낸 건마다 상태가 남고, 반영과 반려 모두 결과로 기록된다.

대표 Edge Case 3개

반려 — PC에서 내용을 확인하고 반려하면?+
보낸 건은 각각 따로 남고, 재고는 PC 확인을 거쳐야 바뀐다. 두 번 보냈다고 재고가 두 번 바뀌지는 않는다.
중복/동시 제출 — 두 번 보내거나 두 명이 동시에 보내면?+
누가 · 어떤 기기에서 보냈는지가 같이 남아 PC 화면에서 구분한다.
모바일과 PC의 재고값 차이+
휴대폰 숫자는 본 순간의 값으로 정의하고, 최종은 반영 시점 기준으로 삼는다. 오류가 아니라 시간 차이다.

모바일·PC 실제 화면 자산은 저장소에 없어 flow와 상태표로 대체한다. 임의 캡처를 만들지 않는다.

Learning

Changed

What changed my mind?

처음에는 PC의 재고 기능을 모바일로 옮기는 문제라고 생각했습니다. 하지만 핵심은 UI가 아니라 “입력값이 언제 실제 재고가 되는가”를 정의하는 것이라는 점을 알게 됐습니다.

Next

What would I validate next?

실제 현장에서 제출 → 검토 → 반영 과정이 얼마나 걸리는지 확인하고, 입력 속도와 재고 정확도 사이의 Trade-off가 적절했는지 검증하겠습니다.
