01

01 WHY — 무엇이 문제였나

두 서비스는 이미 연동돼 있었다. 과제는 새 기능을 만드는 게 아니라, 그 연동에서 개인정보를 다루는 기준이 빠져 있는 것을 찾아 메우는 일이었다.

오가던 정보확인된 상태
약국·회원정보 (파트너몰 → 케어팜)개인정보 제공 동의 없이 전달되는 구간 존재
로그인 연동정보무엇을 모으고 어디까지 넘기는지 기준 불명확
주문 정보 (케어팜 → 파트너몰)전달 사실에 대한 동의·안내 부족
가입 정보가입 경로별 처리 기준 미정의

여섯 가지 질문으로 쪼갬

질문정하는 것
어떤 경로로 들어온 약국인가가입 경로별 구분 (Route)
새로 가입인가, 이미 케어팜 회원인가회원 구분 (Identity)
어떤 정보를 어디로 보내는가전달 항목 (Data)
어떤 조건이면 보내도 되는가동의 조건 (Consent)
지금 가입·약정이 어디까지 진행됐나진행 상태 (State)
언제 어떤 약관에 동의했나동의 기록 (Audit / Log)

02

02 DECISION — 무엇을 선택하고 무엇을 포기했나

기존 사업가치를 유지해야 한다는 제약 안에서, 법률 · 제약사 · 개발 · 영업의 요구를 하나의 실행 가능한 서비스 규칙으로 정리했다. 네 결정 중 기준이 된 것은 D1 흐름 유지와 D2 동의 상태 연결이다.

D1

기능을 지우지 않고, 정보가 오가는 조건을 새로 정한다

대안

문제 되는 연동 기능 삭제

선택

지금 쓰는 흐름 그대로 두고 어떤 조건에서 정보를 넘길지를 규칙으로 정한다.

이유

지우면 파트너몰 → 케어팜 가입 길, 제약사 VIP 혜택, 케어팜 → 파트너몰 주문 길이 함께 사라진다. 쓰던 흐름은 유지한 채 통제하는 쪽을 택했다.

포기한 것

흐름 유지를 택하고 관리 부담 제거를 포기했다. 가입 길·혜택·주문 길을 살리는 대신, 규칙 준수를 시스템과 기록으로 계속 확인해야 한다.

D2

동의 여부만 저장하지 않고, 동의 상태가 전달 여부를 결정하게 한다

대안

화면에 체크박스를 넣고 동의했는지만 저장

선택

동의 상태를 확인해야만 정보가 넘어가도록 연결한다.

이유

실제 전달 시점은 화면 이후 시스템 처리라, 그 시점에 확인해야 막을 수 있다. 저장만 해두면 전달을 막지 못한다.

포기한 것

동의 상태 연결을 택하고 체크박스 저장의 단순함을 포기했다. 동의 없이 들어온 경로는 가입이 끝나지 않고 확인·상담 절차로 이어지는 대신, 조건이 맞을 때만 정보가 넘어간다.

D3

이미 케어팜 회원인 약국이 약정을 맺으면 자격만 추가한다

대안

가입할 때 경로로 회원 종류 고정

선택

새 회원을 만들지 않고 제휴 자격만 추가한다.

이유

이미 케어팜을 쓰던 약국이 나중에 협력도매 약정을 맺는 경우가 있다. 가입 상태와 제휴 자격을 따로 관리해야 한다.

포기한 것

자격 분리를 택하고 회원 종류 고정의 단순함을 포기했다. 관리자 화면과 영업 절차가 구분을 알아야 하는 대신, 기존 회원의 약정 추가가 가능하다.

D4

사람이 처리하는 내부 절차까지 설계 범위에 포함한다

대안

약국이 보는 가입 화면까지만 기획

선택

신청 → 확인 → 영업 상담 → 가입 절차를 함께 설계한다.

이유

자격 없이 신청한 경로는 화면에서 가입이 끝나지 않는다. 화면 밖 절차를 빼면 규칙이 현장에서 깨진다.

포기한 것

운영 절차 포함을 택하고 화면 기획만의 범위를 포기했다. 기획 범위가 넓어지는 대신, 규칙이 현장에서 깨지지 않는다.

03

03 HOW — 어떻게 설계했나

어떤 경로로 들어왔나 → 동의를 받았나 → 무엇을 보내나 → 지금 어디까지 왔나 → 기록에 남았나. 앞 규칙이 정해져야 뒤 규칙이 정해지도록 순서를 고정했다.

법적 요구를 시스템이 판단할 수 있는 조건으로 옮겼다 — 동의했는가는 진입 조건으로, 전달 항목은 필드 정의로, 진행 상태는 다음 단계를 여는 조건으로, 동의 시점은 기록으로 둔다.

Route → Consent → Data → State → Log

규칙내용
가입 경로협력도매 약정 → K제약 VIP, 일반 케어팜 메뉴 → 일반 K제약. 경로마다 다른 값을 전달해 관리자 화면에서 구분한다
회원 구분신규 가입과 제휴 자격을 분리한다. 기존 회원이 약정을 맺으면 자격만 추가한다
전달 항목약국명 · 대표자명 · 약사면허번호 · 사업자등록번호 · 요양기관번호 · 주소 · 생년월일 · 전화번호/휴대폰번호 · 이메일 주소
동의파트너몰 → 케어팜 가입 신청 전 제3자 제공 동의(항목 · 목적 · 보관기간 · 거부 시 안내). 케어팜 → 파트너몰 프로그램 실행 시 연동 동의 확인
진행 상태동의 없음 → 가입 신청 불가. 동의 + 가입 완료 → 약정 신청서 제출 가능. 자격 없이 신청 → 확인 · 영업 상담 연결
동의 기록동의 일시 · IP · 체크 항목을 기록한다

실제로 어떻게 적용했나

  1. 1

    가입

    경로별 구분과 동의 조건을 걸어 신청을 받는다

  2. 2

    약정

    기존 회원은 자격만 추가하고 신규는 가입과 함께 처리한다

  3. 3

    주문

    연동 동의가 확인된 경우에만 주문 정보를 전달한다

  4. 4

    관리자 화면

    경로 · 자격 · 동의 상태를 구분해 보여준다

  5. 5

    영업

    자격 없이 신청한 경로는 확인 · 상담 절차로 연결한다

시스템끼리 주고받는 상세 규격(API Spec)은 아직 정하지 않았다. 개발과 함께 정한다. 임시로 정하면 나중에 바꿀 때 경로 · 동의 · 전달 규칙 전체가 흔들린다.

04

04 RESULT — 무엇이 달라지도록 설계했나

설계 완료 · 개발 대기 상태다. Development Pending / Not Yet Validated — 운영 실적으로 읽히면 안 되므로, 달라진 것이 아니라 달라지도록 설계한 것을 쓴다.

Product Output — 실제로 만들어진 것

  1. 1

    기존 연동

    쓰던 가입 · 주문 흐름은 그대로 둔다

  2. 2

    서비스 규칙

    누락돼 있던 개인정보 처리 기준이 경로 · 동의 · 전달 · 상태 · 기록으로 정해졌다

  3. 3

    시스템

    조건이 맞을 때만 정보가 넘어간다

  4. 4

    사람

    자격 없는 신청은 확인 · 영업 상담으로 이어진다

  5. 5

    기록

    언제 어떤 약관에 동의했는지 남는다

Validated Result — 실제로 확인된 변화

아직 확인된 변화는 없다. 가입 전환 · 주문 연동 건수 · 동의 확보율은 개발과 출시 이후에 잰다.

Measurement — 앞으로 확인할 것

가입 전환 · 주문 연동 건수 · 동의 확보율 같은 숫자는 개발과 출시 이후에 잰다. 아직 측정하지 않았다.

05

05 NEXT — 배운 것과 다음 할 일

이 프로젝트의 차별점은 약관 화면 작성이 아니라, 기존 사업가치를 유지해야 한다는 제약 안에서 법률 · 제약사 · 개발 · 영업의 요구를 하나의 실행 가능한 서비스 규칙으로 정리한 과정에 있다.

What changed my mind?

처음에는 동의 체크박스가 없다는 것이 문제라고 봤다. 전수 확인을 거치니 문제는 체크박스가 아니라 회원 구분 · 정보 전달 · 동의 · 진행 상태 · 기록이 서로 이어져 있지 않은 구조로 바뀌었다 — 그래서 화면이 아니라 규칙과 상태, 시스템 처리와 기록을 함께 정했다.

What was harder than expected?

법률 요구를 시스템이 판단할 수 있는 조건으로 바꾸는 부분이다. 동의했는가를 진입 조건으로, 전달 항목을 필드 정의로, 진행 상태를 다음 단계를 여는 조건으로, 동의 시점을 기록으로 옮겨야 실행 가능한 규칙이 된다.

What would I validate next?

출시 후에는 가입 전환 · 주문 연동 건수 · 동의 확보율을 확인하고, 그 결과에서 규칙을 손본다.
