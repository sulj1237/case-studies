01

WHY · 왜 풀어야 했나

작성 중

상품과 재고를 확인하는 곳은 진열대와 창고인데, 등록과 입력은 PC 앞에서만 할 수 있었다.

Discovery Source — 기존 PC 중심 상품 · 재고 업무 흐름을 검토하는 과정에서, 확인은 현장 · 입력은 PC로 나뉘어 기억 · 메모 · 재입력이 반복되는 구조를 확인. 모바일 입력 요구사항을 정리하던 중 입력값을 바로 재고에 반영해도 되는가라는 두 번째 문제를 발견.

핵심 질문 — 현장에서 입력한 값은 언제부터 실제 재고가 되는가

기존 방식의 한계

  2. 2

확인하는 곳과 입력하는 곳이 떨어져 있어 기억 · 메모 · 이동 · 재입력이 매번 끼어든다.

불편현장에서 벌어지는 일
상품 등록이 PC에서만 가능새 상품을 발견해도 그 자리에서 등록할 수 없다
재고 조사 후 PC에서 다시 입력센 숫자를 옮겨 적는 단계가 한 번 더 있다
조사 상품이 많을수록 왕복 증가진열대와 PC 사이를 반복해서 오간다
기억 · 메모에 의존옮겨 적는 과정에서 숫자가 틀릴 수 있다

요구사항 다음에 나온 진짜 문제

휴대폰 입력 화면을 만드는 것까지는 분명했다. 그 다음 질문이 설계의 중심이 됐다 — 현장에서 입력한 값을 바로 약국 재고에 넣어도 되는가?

잘못된 입력

서서 빠르게 입력하는 환경

상품을 잘못 고르거나 수량을 잘못 누를 수 있다. 그 값이 곧바로 재고가 되면 약국 재고 숫자가 틀어진다.

동시 제출

약사도 기기도 여러 대

같은 상품을 여러 사람이 각자 제출할 수 있다. 어느 값이 맞는지 정할 기준이 필요하다.

재고 불일치

조회한 뒤에도 재고는 움직인다

휴대폰에서 본 사이에 PC에서 판매 · 입고가 일어나면 두 숫자가 달라진다.

기존 업무

PC 중심 운영은 그대로

약국의 재고 운영은 PC에서 돌아간다. 휴대폰이 그 흐름을 흔들면 다른 업무까지 영향을 받는다.

근거 범위 — 기존 업무 흐름 분석과 기획 문서의 구조 변경 이력이 근거다. 현장 소요 시간 · 입력 오류 빈도는 측정 자료 확보 전이다.

02

DECISION · 무엇을 골랐나

작성 중
D1

휴대폰 입력은 PC 확인을 거쳐 재고가 된다

대안

A. 휴대폰에서 입력한 수량을 즉시 전산 재고에 반영

선택

휴대폰 = 입력 · 제출. PC = 확인 · 반영. 실재고 반영 권한은 PC에 둔다.

이유

현장은 서서 빠르게 입력하는 곳이라 오입력이 생긴다. 확인 단계가 있으면 틀린 값이 재고에 닿기 전에 걸린다. 최종 값을 정하는 곳이 한 곳이어야 두 숫자가 다를 때 기준이 선다.

포기한 것

PC 확인 단계를 택하고 즉시 반영의 편리함을 포기했다. 현장 작업 뒤 PC 확인이 남는 대신, 틀린 값이 재고에 닿기 전에 걸리고 최종 값을 정하는 곳이 한 곳으로 유지된다.

구조를 세 번 다시 짰다. 기능 단위로 묶었던 흐름을 데이터의 성격 단위로 다시 나누면서 규칙이 안정됐다.

판단이 바뀐 과정

  1. 1

    06-18 · 한 흐름

    '상품 추가 기능' — 재고 수량 입력 + 상품 수정 + PC 재고 확인을 하나로 묶음

  2. 2

    06-22 · 검수 구조

    앱은 요청 생성, PC는 건마다 승인 · 반려 후 반영

  3. 3

    06-23 · 흐름 분리

    상품 정보(마스터)와 실재고를 별도 흐름으로 분리

  4. 4

    이후 · 반영 모델 확정

    신규 등록 자동 반영 · 정보 수정 선택 반영 · 실재고 덮어쓰기

기록된 변경 근거 — 상품 정보와 실재고는 성격 · 반영 방식 · 책임 주체가 다르다.

D2

상품 정보와 실재고를 별도 흐름으로 나눈다

대안

상품 등록 · 수정과 재고 입력을 한 화면 · 한 제출로 처리

선택

상품 정보는 마스터 흐름(본사 관리자 원본 · PC 선택 반영), 실재고는 재고 흐름(PC 덮어쓰기 반영)으로 분리. 상품 등록 화면에서 재고값 입력을 뺐다.

이유

상품 정보는 여러 약국이 공유하는 마스터로 이어지고, 실재고는 그 약국의 전산 재고만 바꾼다. 반영 방식과 책임 주체가 다른 데이터를 한 흐름에 두면 규칙이 서로 충돌한다.

포기한 것

흐름 분리를 택하고 한 화면 · 한 제출의 편리함을 포기했다. 약사는 상품 등록과 재고 입력을 다른 메뉴에서 하는 대신, 두 데이터가 각자의 반영 방식과 책임 주체를 지킨다.

D3

건별 승인 · 반려 대신 '반영할 건을 고르는' 구조로 둔다

대안

B. PC에서 건마다 승인 · 반려를 판정하고 반려 사유를 입력

선택

PC는 체크한 건만 반영한다. 실재고는 체크하지 않은 항목이 자동으로 반영반려로 기록되고, 상품 정보 수정은 선택하지 않은 요청이 삭제 처리된다. 용어는 반영 · 반영반려로 통일한다.

이유

운영자가 하는 일은 전산에 넣을 값을 고르는 것이다. 동작을 선택 → 반영 하나로 줄이면 반려 버튼 · 사유 입력 단계가 빠지고, 반영하지 않은 건도 상태로 기록이 남는다. 화면에 검수 표현이 남으면 없는 승인 절차가 있는 것처럼 읽혀 용어도 함께 정리했다.

포기한 것

선택 반영을 택하고 건별 반려 사유 기록을 포기했다. 약사는 반영되지 않은 이유를 기록에서 확인할 수 없게 되는 대신, PC의 동작이 선택 → 반영 하나로 줄고 반영하지 않은 건도 상태로 남는다.

D4

실재고는 덮어쓰기로 반영한다

대안

기존 재고에 입력 수량을 더하기 · 반영할 때마다 방식 선택

선택

반영 방식은 덮어쓰기 하나. 반영 후 전산상 재고 = 총 수량(진열 + 창고 자동 합산). 방식 선택 모달은 삭제했다.

이유

실재고는 현장에서 센 실제 보유 수량이다. 그 값 자체가 결과여야 한다. 방식을 매번 고르게 하면 같은 입력이 운영자에 따라 다른 재고가 된다.

포기한 것

덮어쓰기를 택하고 더하기 · 방식 선택을 포기했다. 조회와 반영 사이의 판매분은 반영 시점에 덮이는 대신, 같은 입력은 운영자와 상관없이 같은 재고가 된다 — 그 차이는 반영 기록의 앱 기준 스냅샷으로 남긴다.

D5

중복 제출은 묶어서 보여주고 1건을 고르게 한다

대안

마지막 제출값으로 자동 덮어쓰기

선택

같은 바코드는 묶어서 보여주고, 묶음 안에서 1건만 선택한다. 최신 제출이 기본 선택이고 원본은 모두 보존한다.

이유

자동으로 대체하면 이전 제출을 볼 수 없고, 어느 값을 반영할지 정하는 판단이 PC에서 사라진다. D1의 확정 지점을 중복 제출에도 그대로 적용했다.

포기한 것

1건 선택을 택하고 자동 덮어쓰기를 포기했다. 중복이 많으면 PC에서 고르는 일이 늘어나는 대신, 이전 제출이 모두 보존되고 반영할 값은 PC가 정한다.

03

HOW · 어떻게 만들었나

작성 중

휴대폰 입력 화면과 함께 값이 만들어지고 실제 재고가 되는 순서를 새로 정했다. 값은 입력 → 제출 → 확인 → 반영을 거쳐 실제 재고가 되고, 상태가 바뀌는 지점마다 기록이 남는다.

보낸 값과 약국 재고는 다른 상태로 관리한다

  1. 1

    약사앱

    상품 바코드를 찍는다

  2. 2

    약사앱

    진열 · 창고 수량을 입력한다 — 총 수량은 자동 합산

  3. 3

    약사앱

    제출한다 — 이 값은 반영전 상태의 보낸 값이다

  4. 4

    PC

    제출 목록을 불러온다 — 같은 바코드는 묶여 보인다

  5. 5

    PC

    반영할 건을 체크하고 반영한다

  6. 6

    약국 재고

    체크한 건은 총 수량으로 덮어써 반영완료 · 체크하지 않은 건은 반영반려로 기록

  7. 7

    약사앱

    제출 이력에서 처리 결과를 확인한다

현장에서는 상품 앞에서 바로 입력하고, 약국 재고는 PC에서 반영한 값만 받는다.

앱의 제출 이력은 하루 단위 카드로 **반영전 · 반영중(일부 처리) · 반영완료(완료 + 반려 = 전체)**를 보여준다. 약사는 보낸 값이 어디까지 처리됐는지 PC를 보지 않고 확인한다.

반영완료와 반영반려 모두 보낸 건마다 결과가 기록으로 남는다. 재고가 그대로인 것도 하나의 결과다.

Policy — 입력과 반영 규칙

규칙내용이유
총 수량 자동 합산진열 + 창고 · 직접 입력 불가합계를 따로 입력하면 합과 부분이 어긋날 수 있다
미입력과 0 구분- = 입력 안 함 · 0 = 재고 없음재고 없음과 조사 안 함은 다른 사실이다
재고 보정 사유전산과 총 수량이 다를 때만 노출 · 선택 · 30자차이의 이유를 현장에서 남길 수 있게
원자적 제출전체 성공 또는 전체 실패 · 실패 시 목록 유지 후 재시도일부만 저장되면 무엇이 갔는지 알 수 없다
원본 보존반영 · 반려 후에도 앱 입력값 유지나중에 무엇이 입력됐는지 되짚을 수 있게
용어반영전 · 반영완료 · 반영반려 · 반영실패로 통일검수 · 승인 표현은 없는 절차를 암시한다

모바일 · PC 재고 불일치 — 앱 기준 스냅샷

휴대폰에서 본 전산 재고는 그 순간을 찍은 사진 같은 값이다(앱 기준 스냅샷). 그 사이 PC에서 판매 · 입고가 일어나면 숫자가 달라진다. 이것을 시간 차이로 정의하고, 최종 재고는 반영하는 시점에 정한다. 반영 기록의 수량은 앱 기준 스냅샷으로 남기고, 화면에 한 줄로 안내한다 — 앱 기준(앱 제출 시점의 전산 재고) 값이라 현재 재고와 다를 수 있습니다.

상품 정보 흐름

바코드로 묶어 보여주고 1건만 선택한다. 최신 제출이 기본 선택이고 이전 원본은 보존된다 (D5).

휴대폰에서 본 재고와 PC 재고가 다르다+
앱 기준 스냅샷과 현재 재고의 시간 차이다. 최종 재고는 반영 시점에 총 수량으로 정해진다.
센 수량이 전산 재고와 같다+
보정 사유 입력란이 숨겨진다. 이미 쓴 사유는 세션 안에 보관돼 차이가 다시 생기면 복원된다.

RESULT · 무엇이 정해졌나

작성 중

출시 전이다. 확정된 것은 데이터 상태 모델과 역할 분리다. 현장 효율 · 재고 정확도는 측정된 값이 없다.

Product Output — 설계로 확정된 것

현장 입력 → 제출 → PC 확인 → 반영이라는 데이터 운영 구조를 설계한 것이 결과다. 휴대폰은 입력 · 제출, PC는 확인 · 반영으로 역할을 나누고, PC에서 반영한 값만 실제 재고가 된다.

기존설계 후
입력하는 곳PC 앞상품이 있는 현장
실제 재고가 되는 시점입력 즉시PC에서 반영한 순간

상품 정보와 재고한 흐름마스터 흐름 · 재고 흐름 분리

데이터 상태

보낸 값과 실제 재고를 분리

반영전 → 반영완료 · 반영반려 · 반영실패. 실제 재고가 바뀌는 지점은 하나다.

역할

Mobile = 입력 · PC = 확인 · 반영

최종 반영 권한을 PC에 두어 두 숫자가 다를 때 기준이 선다.

운영

기존 PC 업무 유지

휴대폰은 기존 PC 업무 위에 입력 채널로 추가된다.

추적

누가 · 무엇을 · 언제

입력자 · 처리자 · 처리결과 · 앱 기준 수량이 반영 기록에 남는다.

Validated Result — 실제로 확인된 변화

Business / User Result — 측정 전. 출시 전 단계다.

Measurement — 앞으로 확인할 것

KPI 정의 전 — 측정 항목은 기획 원문에 성공 지표가 정해지면 이 자리에 둔다.

05

NEXT · 한계와 다음 반복

작성 중

모바일 UX보다 데이터가 언제 실제 값이 되는가를 먼저 정의해야 했다. 그 지점을 PC의 반영으로 정하자 역할 분리와 상태 설계가 따라 정해졌다.

What changed my mind?

PC 화면을 휴대폰으로 옮기는 일로 시작했다. 처음에는 '상품 추가 기능' 하나로 묶었지만, 상품 정보와 실재고는 반영 방식 · 책임 주체가 달라 한 흐름에 두면 규칙이 계속 충돌했다. 기능 단위를 데이터 성격 단위로 바꿔 나누고 나서 구조가 멈췄다.

What was harder than expected?

'틀린 숫자'와 '시간 차이'를 구분하는 일. 휴대폰과 PC 재고가 다른 상황을 오류로 두면 대응할 방법이 없다. 본 순간의 값(스냅샷)으로 정의하자 안내 문구와 기록 방식이 정해졌다.

용어를 규칙에 맞추는 일. 검수 · 승인이라는 말이 남아 있으면 없는 승인 절차가 있는 것처럼 읽힌다. 반영 모델이 바뀔 때 용어 목록까지 함께 고쳐야 문서와 화면이 같은 규칙을 말했다.

다음에 개선할 점

실재고 반영 권한 범위와 반영 일부 실패 시 처리 방식이 정해져야 운영 흐름이 닫힌다.
