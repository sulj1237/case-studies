01

INTRO

약국 문의 처리 기록의 재설계

본사 관리자의 A/S 관리 화면은 약국 문의를 받는 CS팀(상담사)과 기술 처리를 맡는 엔지니어가 함께 쓴다. 이 화면에 문의가 들어와서 끝날 때까지의 처리 흐름(Case Workflow)을 더하는 프로젝트다.

↓
02

PROBLEM

처리 시점과 이관이 남지 않는 기록

A/S 기록은 매달 1,100건 넘게 쌓였지만, 언제 처리됐는지 · 누구에게 넘어갔는지 · 어떤 문의였는지는 기록으로 알 수 없었다. 그래서 운영 지표를 낼 수 없었다.

운영 데이터에서 확인한 것

6개월치 A/S 기록 7,309건을 직접 분석했다. 원본에는 약국명 · 연락처가 있어 분석은 로컬에서만 하고, 여기에는 집계 비율만 쓴다.

기존 카테고리 는 제품 · 시스템 기준이라 문의 유형을 따로 알 수 없었다. 키워드 규칙으로 96%가 분류된 것을 근거로, 유형은 CS가 고르지 않고 시스템이 채우는 방향으로 정했다.

↓
03

ANALYSIS

입력은 그대로, 기록은 자동으로

데이터만 보면 입력 칸을 늘리는 쪽이 정확하다. 하지만 CS팀은 전화를 받으면서 기록한다. 그래서 입력은 늘리지 않고, 시스템이 알 수 있는 것은 자동으로 남기는 쪽을 택했다.

01

CS팀 의견으로 바꾼 설계

CS팀 질문서(10문항)를 만들어 상담사 3명에게서 두 차례 답을 받았다. 실무 반박 4건을 받아 설계를 바꿨다.

02

1차 범위 재정의

설계를 다시 보니 고도화의 이득은 관리 · 개발 쪽에 몰리고, CS에게는 입력 부담만 늘 수 있었다. 그래서 1차 범위를 다시 정했다.

합격 기준 — 릴리스 2주 뒤 "CS 손이 더 가는가"를 확인하고, 더 가는 기능은 뺀다.

↓
04

SOLUTION

상태 2개와 자동 기록 구조

상태는 둘로 줄이고, 담당 · 이관 · 시각은 사람이 아니라 시스템이 기록한다. 상담사와 엔지니어 사이의 넘기기와 되돌리기는 정해진 흐름으로 남는다.

01

처리 흐름

  1. 1

    상담사

    약국 관리에서 A/S 등록 — 등록 즉시 확인중

  2. 2

    상담사 → 엔지니어

    넘기기 — 넘긴 사람 · 받은 사람 · 시각 자동 기록

  3. 3

    엔지니어 → 상담사

    보완 요청 — 요청 내용을 적고 상담사에게 되돌린다

  4. 4

    처리한 사람

    처리완료 — 담당이 처리한 사람으로 자동 갱신, 필요하면 처리 불가 표시

02

누가 무엇을 기록하는가

05

RESULT

처리 기록과 운영 지표의 기반

설계 중인 결과다. 출시 전이라 실제 지표는 아직 없다. 이 설계로 1차부터 정확하게 낼 수 있는 지표를 먼저 정했다.

1차부터 낼 수 있는 운영 지표

접수부터 종료까지의 시간은 접수일시를 사람이 고칠 수 있어 참고값으로만 쓴다.
