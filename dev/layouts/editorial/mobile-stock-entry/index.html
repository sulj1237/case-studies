01

PROBLEM

재고 확인과 입력 공간의 분리

약국 재고는 진열대·창고에서 확인하지만, 입력은 PC 클라이언트(약국의 기존 업무 프로그램) 앞에서만 할 수 있어 약사가 기억·메모·이동·재입력을 반복했다. 그렇다고 약사앱(현장에서 상품을 등록하고 실재고를 입력·제출하는 모바일 서비스)에 입력한 값을 바로 실제 재고로 반영하면, 검토되지 않은 값이 전산 재고에 들어갈 수 있었다.

02

ANALYSIS

입력값 · 상품 정보 · 실재고의 역할 분해

입력은 현장으로 옮기되, 입력값이 실제 재고가 되는 시점은 따로 정했다. 모바일에서 입력한 값은 바로 실제 재고에 반영하지 않는다.

01

판단해야 했던 문제 → 결정한 방향

결정

현장에서 입력한 값을 언제 실제 재고에 반영할 것인가?

바로 반영하지 않는다. 모바일 입력 → 제출 → PC 확인 → 실제 재고 반영

모바일과 PC가 같은 일을 하게 둘 것인가?

앱은 입력·제출, PC는 확인·반영으로 역할을 겹치지 않게 나눈다

상품 정보와 실재고를 하나의 흐름으로 관리할 것인가?

별도 흐름으로 관리한다 — 상품 정보는 상품 마스터로, 실재고는 약국 재고로

제출된 값이 어떻게 처리됐는지 어떻게 알 것인가?

제출값마다 상태와 처리 이력을 남긴다

바코드로 묶어 구분하고, 최신 제출을 기본 선택하되 원본은 보존한다

03

SOLUTION

입력과 반영을 나눈 데이터 흐름 설계

약사앱에서 만든 값은 제출 데이터로 저장되고, PC 클라이언트에서 확인·선택한 항목만 실제 약국 재고가 된다. 상품 정보는 별도 흐름으로 슈퍼어드민의 상품 마스터에 모인다.

앱은 입력·제출, PC는 확인·반영, 슈퍼어드민은 상품 마스터를 맡는다.

01

상품·실재고 데이터 흐름

  1. 1

    약사앱

    바코드 스캔 → 상품 등록·수정 / 실재고 입력 → 제출

    →
  2. 2

    제출 데이터

    상품 정보 / 진열·창고 수량 → 반영 전 데이터로 저장

    →
  3. 3

    PC 클라이언트

    제출 내용 확인 → 필요한 항목 선택 → 반영

    →
  4. 4

    약국 재고

    PC에서 반영한 총 수량을 실제 전산 재고로 적용

02

Role Separation · 플랫폼별 역할

실재고는 약국 운영 데이터로, PC 클라이언트에서 최종 반영한다. 슈퍼어드민은 여러 약국이 쓰는 상품 마스터와 변경 이력을 관리한다.

03

상품 정보와 실재고를 분리

04

상태

제출된 값이 어느 단계에 있는지 나눠, 아직 반영되지 않은 값이 실제 재고처럼 보이지 않게 했다.

  1. 1

    제출

    앱에서 보낸 현장 확인값 — 아직 재고 아님

    →
  2. 2

    PC 확인을 기다리는 값 — 전산 재고와 구분

    →
  3. 3

    PC 확인

    반영할 항목 선택 — 선택하지 않은 항목은 반영반려

    →
  4. 4

    반영 완료

    선택한 값이 실제 재고로 적용

05

정책

  • 모바일 입력값은 제출 데이터로 저장한다
  • 반영 전 데이터와 실제 재고를 구분해 보여준다 — 반영되지 않은 값은 실제 재고와 같은 값으로 취급하지 않는다
  • PC에서 확인한 뒤 실제 재고에 반영한다 (반영 시점의 총 수량으로 덮어쓰기)
  • 제출자 · 제출 시간 · 수량 · 처리 상태를 기록한다
06

예외 상황

예외가 생겨도 입력값과 실제 재고의 기준이 섞이지 않도록 처리 방식을 정했다.

여러 약사가 같은 상품을 제출+
바코드로 묶어 구분하고 1건만 선택한다 — 최신 제출이 기본 선택이며, 나머지 원본 기록은 보존한다
제출 중 네트워크가 끊김+
제출은 전체 성공 또는 전체 실패로 처리한다 — 실패하면 제출 목록을 그대로 두고 다시 시도한다
앱과 PC의 재고 차이+
앱 입력값은 입력 시점의 현장 확인값, 실제 재고는 PC에서 반영하는 시점의 값으로 구분한다
기존 전산 재고와 입력값이 동일+
재고 보정 사유 입력란은 전산 재고와 총 수량이 다를 때만 보인다 · 이미 쓴 사유의 보관 방식은 검토 필요
