02 PROBLEM · 현장과 입력이 분리된 재고 업무

약국 상품 및 재고 관리 시, 상품 확인은 현장(진열대·창고)에서, 입력은 PC 앞에서만 가능했다. 결국, 약사는 기억·메모·이동·재입력을 반복해야 했다.

03 DECISION

현장에서 바로 입력 모바일로 업무를 옮기면서, 입력값·상품 정보·실제 재고의 역할과 반영 기준을 분리했다.

판단해야 했던 문제 → 결정한 방향

04 HOW

현장에서 입력한 데이터와 실제 재고를 분리하고, 약사앱 → 서버 → PC → 약국 재고로 이어지는 흐름을 설계했다.

앱은 입력·제출, PC는 확인·반영, 슈퍼어드민은 상품 마스터를 관리한다.

상품·실재고 데이터 흐름

  1. 1

    약사앱

    바코드 스캔 → 상품 등록 / 실재고 입력 → 제출

    →
  2. 2

    제출 데이터

    상품 정보 / 진열·창고 수량 → 반영 전 데이터로 저장

    →
  3. 3

    PC 클라이언트

    제출 내용 확인 → 필요한 건 선택 → 실제 재고 반영

    →
  4. 4

    약국 재고

    PC에서 반영한 총 수량을 실제 전산 재고로 적용

Role Separation · 플랫폼별 역할

슈퍼어드민에서 실재고를 관리하는 것이 아니다. 실재고는 약국 운영 데이터이며 PC 클라이언트에서 최종 반영된다.

상품 정보와 실재고를 분리

데이터 성격과 책임 주체가 다르기 때문에 흐름을 분리

상태

제출 데이터의 처리 상태를 구분해 입력값과 실제 재고의 경계를 관리했다.

    선택·검토

    →
  4. 4

    반영 완료

    실제 재고 적용

정책

입력값의 오류와 데이터 혼선을 줄이기 위해 수량·상태·반영 기준을 각각 했다.

예외 상황

중복 제출·네트워크 오류·재고 차이 등 예외 상황에서도 입력값과 실제 재고의 기준이 섞이지 않도록 처리 구조를 분리했다.

여러 약사가 같은 상품을 제출+
바코드로 묶어 1건만 선택 — 최신 기본, 원본 보존
제출 중 네트워크가 끊김+
전체 실패 처리, 제출 목록 유지 — 다시 시도
앱과 PC의 재고 차이+
스냅샷과 현재 재고의 시간 차이 — 최종 재고는 반영 시점 총 수량
기존 전산 재고와 입력값이 동일+
보정 사유 입력란 숨김 — 쓴 사유는 세션 보관

구조 요약

하나의 재고 입력 기능이 아니라, 현장 데이터 생성 → 검토 → 실제 재고 반영 → 상품 마스터 관리의 역할과 데이터 경계를 분리해 설계했다.

05 RESULT

현장에서 입력하고, PC에서 확정하는 재고 관리 구조

PC에서만 입력하던 재고 업무를 현장으로 옮기고, 입력 데이터와 실제 재고를 분리해 관리 했다.

재고 확인과 입력을 한 공간에서
